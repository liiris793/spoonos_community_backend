# SpoonOS 社区共建 Bot｜中文测试执行包

这份文件按“准备 → 提交 → 预审 → 审核 → 发分”的真实操作顺序编写。
正文说明使用中文；需要提交给英文社区的模拟用户内容使用英文，避免语言本身影响测试结果。

## 一、开始前准备

### 1. 准备两个终端

终端 A：在项目根目录启动 AI 预审服务。Bot 和预审服务共用根目录
`.env`，不需要另外创建 `review-service/.env`。

```bash
cd "/Users/diana/Documents/New project 2"
npm run dev:review
```

终端 B：启动 Discord Bot。

```bash
cd "/Users/diana/Documents/New project 2"
npm run deploy:commands
npm run dev
```

### 2. 检查 AI 是否开启

```bash
curl http://127.0.0.1:8000/health
```

预期：

```json
{"ok":true,"aiEnabled":true}
```

### 3. 准备测试账号

最好准备：

- 测试用户 A：提交大部分任务。
- 测试用户 B：测试重复内容和不同用户提交。
- 运营账号：发布任务、查看预审、导出和审核。

如果只有一个测试账号也可以，但要注意任务的每日、每周提交次数限制。

### 4. 发布测试任务

运营账号依次执行：

```text
/task-admin status task_id:T005 status:Published
/task-admin status task_id:T006 status:Published
/task-admin status task_id:T012 status:Published
/task-admin status task_id:T022 status:Published
/task-admin status task_id:T001 status:Published
```

## 二、普通任务提交测试

用户提交后只应该看到：

```text
Submission received: sub_xxx
Status: Prechecked
```

用户不应该看到 AI 分数、风控标签、反作弊原因和内部审核问题。

此时只完成本地规则检查，不会调用 Agnes AI。需要在前一个完整 UTC 日结束后，由运营执行：

```text
/review export start_date:YYYY-MM-DD end_date:YYYY-MM-DD ai_precheck:True ai_limit:5
```

导出的`ai_details`中出现`_provider.model`才表示模型真实返回了结果。
审核表中的`ai_suggested_decision`、`ai_suggested_points`和`ai_reason`只作为运营参考。
最终需要填写`review_decision`，通过时填写`final_points`或`quality_coefficient`；
选择`reject`或`revision`不会发放积分。

运营账号可以立即执行：

```text
/review next
```

查看预审结果。当天提交的数据不能在当天按完整 UTC 日导出，可以第二天使用 `/review export`。

## 三、AI 异常测试

### TC-AI-01｜关闭 AI 服务后提交

先在运行 Python 服务的终端按 `Ctrl+C`。

然后提交一条新的 T005 测试建议。

预期：

- 用户仍收到 `Submission received`。
- 提交不会丢失。
- 状态仍可以进入 `Prechecked`。
- 运营侧看到 `ai_service_unavailable`。
- 建议为人工 `review`。
- Bot 不崩溃、不自动发分。

测试后重新启动 Python 服务。

### TC-AI-02｜检查 Agnes 兼容模式

正常提交一条 T005 或 T006。

在导出的 `ai_details` 中查看：

```json
"_provider": {
  "model": "agnes-2.0-flash",
  "compatibilityMode": false
}
```

如果 `compatibilityMode` 为 `true`，说明 Agnes 拒绝了 JSON Mode 参数，服务已经自动用基础 Chat Completions 格式重试。这不算测试失败。

## 四、每日活跃测试消息

先在项目根目录 `.env` 中填写测试频道 ID：

```dotenv
ACTIVITY_CHANNEL_IDS=你的测试频道ID
```

修改后重启 Bot。

### TC-ACT-01｜应该被过滤的消息

测试用户 A 在指定频道逐条发送：

```text
gm
```

```text
gn
```

```text
nice
```

```text
🔥🔥🔥
```

```text
https://example.com
```

预期：

- 分别被识别为问候、过短、纯表情或纯链接。
- 不计入每日五条有效消息。

### TC-ACT-02｜应该计入候选的五条消息

测试用户 B 在指定频道逐条发送：

```text
I tested the Arena retry flow today. Keeping the previous prompt after an error would reduce repeated work.
```

```text
The current loading state should explain whether the agent is waiting for a tool result or generating the final response.
```

```text
The onboarding FAQ needs one screenshot showing how a beginner selects the correct community role.
```

```text
Does the current Skill Marketplace ranking consider recent usage, total installs, or both?
```

```text
I reproduced the workflow issue on desktop Chrome and documented the exact steps in the product feedback channel.
```

预期：

- Python 基础规则应允许它们进入 AI 相关性判断。
- AI 应分别返回相关性、质量分数和理由。
- 达到五条不代表自动发分，只生成预审建议。

### TC-ACT-03｜非指定频道不计入

把上面任意一条有效消息发送到未配置的频道。

预期：不会进入 T001 消息库。

### TC-ACT-04｜删除消息

在指定频道发送一条有效消息，随后删除。

预期：该消息被标记删除，在日结预审时排除。

### TC-ACT-05｜查看当天采集状态

运营账号执行：

```text
/activity-admin status date:当前UTC日期
```

预期：显示已采集消息数、用户数、已生成的每日审核记录数。

### TC-ACT-06｜历史消息补采

选择一个已经结束、且频道内确实存在消息的 UTC 日期：

```text
/activity-admin collect channel:#测试频道 date:YYYY-MM-DD
```

连续执行两次。

预期：

- 第一次保存历史消息。
- 第二次不会重复保存相同 Discord Message ID。

### TC-ACT-07｜执行每日预审

```text
/activity-admin precheck date:已经结束的UTC日期
```

预期：

- 按用户生成 T001 `Prechecked` 提交。
- 包含候选消息数、规则通过数、AI 有效数、建议积分。
- 不直接发放积分。

如果使用当前 UTC 日期，应提示：

```text
Activity prechecks can only run for a completed UTC day.
```

## 六、批量审核测试

建议使用独立测试数据库执行本节：

```dotenv
DATABASE_PATH=./data/acceptance-test.db
```

### TC-REV-01｜混合审核结果

在导出的表格中选择三条，分别填写：

第一条：

```text
review_decision = approve
quality_coefficient = 1
review_note = Evidence verified in the acceptance test.
```

第二条：

```text
review_decision = revision
quality_coefficient = 留空
review_note = Please add the missing source and your own analysis.
```

第三条：

```text
review_decision = reject
quality_coefficient = 留空
review_note = The submission is non-substantive and does not meet the task requirements.
```

上传：

```text
/review import file:填写完成的审核表
```

预期：

- 仅 `approve` 获得积分。
- 另外两条分别变为 `RevisionRequired`、`Rejected`。
- 审核理由保存并尝试通过 DM 通知用户。

### TC-REV-02｜重复上传审核表

再次上传完全相同的表格。

预期：

- 已完成记录被跳过。
- 不重复发放积分。

### TC-REV-03｜质量系数

批准一条任务时填写：

```text
quality_coefficient = 1.25
```

预期：最终积分等于基础积分 × 1.25，但不能超过任务的 `maxPoints`。

## 七、最终通过标准

以下结果全部满足，即可开始小范围试运营：

- 高质量、低质量、缺失材料和重复提交可以被区分。
- AI 失败不会导致提交丢失或 Bot 崩溃。
- 用户看不到内部 AI 风控信息。
- AI 不会直接批准、驳回或发放积分。
- 只有指定频道消息可以进入 T001。
- 低价值发言无法满足每日有效消息要求。
- 重复导入审核表不会重复发分。
- 排行榜积分与 point ledger 完全一致。
